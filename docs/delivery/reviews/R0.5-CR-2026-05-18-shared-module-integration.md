## 3. 阻断问题

### P0-1 前端生产构建失败

证据：

- 文件：`clients/dandelion/frontend/app/admin/page.tsx`
- 问题行：导入 `getDashboard`、`getLeads`、`updateLeadStatus`
- 文件：`clients/dandelion/frontend/lib/api.ts`
- 实际只导出 `API_BASE`、`LeadPayload`、`createLead`、`trackEvent`

影响：

- 官网无法生产构建。
- Admin 页面不可用。
- 当前代码不能部署或演示完整闭环。

修复要求：

- 在后端补齐 Admin/Dashboard API 后，再在 `lib/api.ts` 实现对应 client 方法。
- 或临时移除 Admin 页面对不存在 API 的依赖，但这只能作为短期降级，不符合本阶段闭环目标。

推荐接口契约：

```ts
getDashboard(): Promise<{
  total_leads: number;
  audit_submits: number;
  booking_clicks: number;
  cta_clicks: number;
  statuses: { status: string; count: number }[];
  sources: { source: string; count: number }[];
}>

getLeads(): Promise<{ leads: AdminLead[] }>

updateLeadStatus(leadId: string, status: string): Promise<AdminLead>
```

验收：

- `npm run build` 通过。
- Admin 页面能加载 dashboard 与 lead queue。
- 状态更新后页面刷新能看到最新状态。

### P0-2 客户后端默认没有连接 MySQL

证据：

- 文件：`packages/backend/dandelion_core/config/client_config.py`
- 当前实现：模块 import 时执行 `load_dotenv()`，但没有明确加载客户项目 `.env`。
- 在 `clients/dandelion/backend` 中运行 `ClientConfig.from_env()`，实际输出 `sqlite:///./dandelion.db`。

影响：

- 本地已创建的 MySQL 表不会被默认使用。
- 运行环境可能写入 SQLite 文件，导致数据丢失、环境不一致和测试误判。

修复要求：

- 客户 app 必须显式加载客户目录 `.env`，不能依赖共享 package 的 import side effect。
- `ClientConfig.from_env()` 应在调用时读取环境变量，而不是在 class field 定义时固定读取。
- 后端依赖必须包含 `python-dotenv`、`sqlalchemy`、`pymysql`、`fastapi`、`uvicorn`、`pydantic`、`email-validator`。

推荐实现方向：

```python
class ClientConfig(BaseModel):
    ...

    @classmethod
    def from_env(cls, env_file: str | None = None):
        if env_file:
            load_dotenv(env_file, override=False)
        return cls(
            project_name=os.getenv("PROJECT_NAME", "Dandelion Software"),
            client_key=os.getenv("CLIENT_KEY", "dandelion"),
            database_url=os.getenv("DATABASE_URL", "sqlite:///./dandelion.db"),
            ...
        )
```

客户 app 中应传入明确路径：

```python
BASE_DIR = Path(__file__).resolve().parent
config = ClientConfig.from_env(BASE_DIR / ".env")
```

验收：

- 在 `clients/dandelion/backend` 默认运行配置检查，输出 MySQL URL。
- 启动后不再生成或写入 `dandelion.db`。
- 表单提交写入 `dandelion_website_db.leads`。

### P0-3 Admin/Dashboard 后台闭环未实现

证据：

- 文件：`clients/dandelion/backend/main.py`
- 当前只挂载 `create_leads_router` 与 `create_events_router`。
- 共享模块目录只有 `leads`、`events`，缺少 `admin_crm`、`dashboard`、`notifications` 等设计文档要求的可用实现。

影响：

- 产品定义的“网站 + 运营轻量化闭环”没有完成。
- 前端 Admin 页面无法与后端对接。
- 当前系统只完成了公开提交和事件记录的一部分，不具备客户后台运营能力。

修复要求：

- 实现 `dashboard` 模块：基础汇总、状态分布、来源分布、事件计数。
- 实现 `admin_crm` 模块：lead list、lead detail、status update、notes。
- 实现 `notifications` 基础模块：至少记录 notification log，MVP 可以先 mock 发送。
- 客户 app 按 config 挂载模块。

验收：

- `GET /api/admin/dashboard` 返回 Admin 页面需要的数据。
- `GET /api/admin/leads` 返回 lead queue。
- `PATCH /api/admin/leads/{lead_id}/status` 可以更新状态。
- `GET /api/admin/leads/{lead_id}` 返回详情和 notes。
- 后台接口全部需要 admin key。

### P1-1 后台数据接口未鉴权

证据：

- 文件：`packages/backend/dandelion_core/modules/leads/router.py`
- 当前 `GET /api/leads/` 公开返回 lead list。

影响：

- 线索数据包含姓名、邮箱、电话、业务信息，不能公开暴露。
- 即使 MVP 也会形成错误架构习惯，后续客户项目复制时风险扩大。

修复要求：

- 公开接口只保留 `POST /api/leads/`。
- 后台读取、更新、详情、notes、dashboard 均迁移到 `/api/admin/*`。
- 使用 `ADMIN_API_KEY` 做 MVP 鉴权，header 推荐为 `X-Admin-Key`。
- 未配置 `ADMIN_API_KEY` 时，仅允许 development 环境开放，生产环境必须拒绝启动或拒绝后台接口。

验收：

- 无 key 请求后台接口返回 `401` 或 `403`。
- 正确 key 可以访问。
- 公开提交 lead 不需要 admin key。

### P1-2 migration、ORM、实际表结构不一致

证据：

- ORM：`events.lead_id` 定义了 `ForeignKey("leads.lead_id")`。
- SQL migration：`events.lead_id` 只有普通索引，没有外键约束。
- migration 只创建 `leads`、`events`。

影响：

- 数据完整性依赖应用层，数据库不会阻止孤儿 event。
- 新环境用 SQL migration 和用 ORM `create_all` 得到的 schema 不完全一致。
- 后续排查数据问题困难。

修复要求：

- 明确 migration 是唯一 schema 来源。
- 补齐 FK 约束。
- 补齐后台闭环需要的表。
- 移除生产启动时的 `Base.metadata.create_all()`。

验收：

- 全新 MySQL 数据库通过 migration 初始化。
- `SHOW CREATE TABLE` 与 ORM 设计一致。
- 删除/更新策略明确，建议 event 对 lead 使用 `ON DELETE SET NULL` 或业务禁止删除 lead。

### P1-3 查询索引不完整

证据：

当前 MySQL 只有：

- `leads(last_activity_at)`
- `leads(status, last_activity_at)`
- `leads(industry, last_activity_at)`
- `events(occurred_at, event_type)`
- `events(lead_id)`

设计和实际查询还需要支持：

- Admin 按 source/campaign/status 查询。
- Dashboard 按时间范围统计事件。
- Session/visitor 追踪。
- Notification retry。
- Lead notes 时间线。

修复要求：

至少补充：

```sql
CREATE INDEX idx_leads_source_activity ON leads (source, last_activity_at DESC);
CREATE INDEX idx_leads_campaign_activity ON leads (campaign, last_activity_at DESC);
CREATE INDEX idx_leads_form_activity ON leads (module_source, form_key, last_activity_at DESC);
CREATE INDEX idx_events_session_time ON events (session_id, occurred_at DESC);
CREATE INDEX idx_events_source_time ON events (source, occurred_at DESC);
CREATE INDEX idx_events_module_form_time ON events (module_source, form_key, occurred_at DESC);
```

如果实现 notes/notifications，还需要：

```sql
CREATE INDEX idx_lead_notes_lead_created ON lead_notes (lead_id, created_at DESC);
CREATE INDEX idx_notification_logs_status_retry ON notification_logs (status, next_retry_at);
CREATE INDEX idx_notification_logs_lead_created ON notification_logs (lead_id, created_at DESC);
```

验收：

- Admin lead list 查询使用已有 index。
- Dashboard 时间范围查询使用已有 index。
- `SHOW INDEX` 能看到对应索引。

## 4. 非阻断但必须修复的问题

### P2-1 Repository 内部直接 commit

证据：

- `LeadRepository.create()` 内部执行 `session.commit()`。
- `EventRepository.create()` 内部执行 `session.commit()`。

影响：

- service 无法组合 lead、event、notification 为一个事务。
- 测试 fixture 的 rollback 无法可靠隔离。
- 中途失败时容易产生半完成数据。

修复要求：

- repository 只 `add/flush/refresh`，不负责 commit。
- service 或 request transaction middleware 负责 commit/rollback。

### P2-2 mutable default

证据：

- SQLAlchemy model 使用 `default={}`、`default=[]`。
- Pydantic schema 使用 `metadata: Dict[str, Any] = {}`。

修复要求：

- SQLAlchemy 使用 callable default，例如 `default=dict`、`default=list`。
- Pydantic 使用 `Field(default_factory=dict)`、`Field(default_factory=list)`。

### P2-3 Pydantic v2 deprecation

证据：

- 测试输出 `PydanticDeprecatedSince20`。

修复要求：

- 使用 `ConfigDict(from_attributes=True)` 替换 class-based `Config`。

### P2-4 依赖与部署不可复现

证据：

- `clients/dandelion/backend` 没有独立依赖文件。
- `backend_old/.venv` 缺少 `dotenv/sqlalchemy/pymysql`。
- `clients/dandelion/docker-compose.yml` backend build 指向 `./backend`，但当前 backend 目录没有 Dockerfile。

修复要求：

- 为共享 backend package 和客户 backend app 建立明确依赖管理。
- 删除或隔离 `backend_old`，避免部署脚本误用。
- 补齐 backend Dockerfile 或修正 compose。
