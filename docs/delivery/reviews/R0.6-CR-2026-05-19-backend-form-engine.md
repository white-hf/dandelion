## 3. Findings

### P0-1 客户默认 `.env` 已被破坏，真实 app 回退 SQLite

证据：

- 文件：`clients/dandelion/backend/.env`
- 当前内容只有：

```text
PROJECT_NAME=Dandelion
```

- 真实 client app 验证输出：

```text
db sqlite:///./dandelion.db
admin False
```

影响：

- 这直接回退了 R0.5 的核心结论：客户 app 默认应连接 MySQL，并配置 `ADMIN_API_KEY`。
- 架构师报告中“未显式传入环境变量时自动安全回退到 SQLite”不是安全行为，而是部署回归。
- 当前默认 app 不会使用已创建的 MySQL `form_configs`，动态表单在真实客户路径不可用。

修复要求：

- 恢复 `clients/dandelion/backend/.env`，至少包含 `DATABASE_URL`、`ADMIN_API_KEY`、`ENV`、`PORT`。
- 禁止把 SQLite fallback 作为客户 app 的正常运行路径。
- 在 `clients/dandelion/backend/main.py` 或 `ClientConfig` 增加 fail-fast：客户环境缺少 `DATABASE_URL` 或 `ADMIN_API_KEY` 时不得静默启动。
- 找出 `.env` 被覆盖为单行的来源，优先修复 `scripts/setup_environment.sh` 的 env 写入逻辑。

验收：

```bash
cd clients/dandelion/backend
PYTHONPATH=../../../packages/backend ../../../packages/backend/.venv/bin/python - <<'PY'
import main
assert main.config.database_url.startswith("mysql+pymysql://")
assert main.config.admin_api_key
print("CONFIG_OK")
PY
```

### P1-1 `0002_form_configs.sql` 非幂等，重复执行失败

证据：

执行：

```bash
mysql -h127.0.0.1 -uwebsite_user -p'user@Halifax' dandelion_website_db < packages/backend/dandelion_core/database/migrations/0002_form_configs.sql
```

结果：

```text
ERROR 1061 (42000) at line 18: Duplicate key name 'idx_form_configs_industry'
```

影响：

- `scripts/setup_environment.sh` 当前会扫描并应用所有 `.sql` migration。
- 一旦重复执行部署脚本，`0002` 会失败。
- 这违反 R0.5 后建立的 migration safety baseline。

修复要求：

- migration 文件本身必须可重复执行，或引入 migration history table 防止重复执行。
- MySQL 8 可用 `CREATE INDEX` 前查询 `information_schema.statistics`，或把 index creation 移入 setup script 的 idempotent index loop。
- 不允许让部署脚本在正常二次执行时失败。

验收：

```bash
mysql -h127.0.0.1 -uwebsite_user -p'user@Halifax' dandelion_website_db < packages/backend/dandelion_core/database/migrations/0002_form_configs.sql
mysql -h127.0.0.1 -uwebsite_user -p'user@Halifax' dandelion_website_db < packages/backend/dandelion_core/database/migrations/0002_form_configs.sql
```

两次都必须成功。

### P1-2 动态 required 字段校验未实现

证据：

- 文件：`packages/backend/dandelion_core/modules/forms/service.py`
- 当前代码明确写着：

```python
# Note: In a full implementation, we'd iterate config.schema_json['fields']
```

- 验证中创建了 schema：

```json
{"fields":[{"name":"need","label":"Need","type":"text","required":true}]}
```

- 提交缺少 `need` 的 payload 仍返回 `200` 并创建 lead：

```text
missing_required 200
```

影响：

- 这不满足 `Iteration_Plan.md` 的 I0.6.1 范围：“动态字段校验逻辑”。
- 会导致无效线索进入 CRM，前端即使渲染 required 字段，后端也无法兜底。

修复要求：

- 遍历 `config.schema_json["fields"]`。
- 对 `required=true` 的字段检查 `submission.data`。
- 对基础类型做最低限度校验：`text/textarea/email/phone/select/checkbox/date`。
- `select` 必须验证提交值在 `options` 中。
- 校验失败返回 `422`，包含字段级错误。

验收：

- 缺少 required 字段返回 `422`。
- 非法 select option 返回 `422`。
- 合法 payload 返回 `200`，并创建 lead/event。

### P1-3 forms 未纳入自动化测试

证据：

- 文件：`packages/backend/tests/test_system.py`
- 当前只挂载 leads/events/dashboard/admin_crm。
- 没有 `create_forms_router`。
- pytest 仍然只有 `4 passed`，没有任何 forms 测试。

影响：

- I0.6.1 的核心能力没有进入 CI/回归测试。
- 当前通过的 pytest 不能证明动态表单引擎可用。

修复要求：

- 在 pytest 中挂载 `create_forms_router`。
- 增加至少以下测试：
  - active config exists -> valid submission returns 200。
  - missing config -> 404。
  - missing required field -> 422。
  - successful submission creates lead and event in same transaction。
  - default client app config uses MySQL or test-specific override，不允许意外 SQLite。

### P1-4 缺少 schema 读取 API，前端 FormRenderer 无法配置驱动

证据：

- `packages/backend/dandelion_core/modules/forms/router.py` 只提供 `POST /api/submissions/`。
- 没有公开或受控的 `GET /api/forms/{form_key}` / `GET /api/form-configs/{form_key}`。
- `FormConfigResponse` 已定义但没有被任何 route 使用。

影响：

- 架构师建议下一步开发 `FormRenderer.tsx`，但前端没有 API 获取 `schema_json`。
- 如果让前端硬编码 schema，会违背 M0.6 的“配置驱动”目标。

修复要求：

- 增加只读 form config endpoint，例如：

```text
GET /api/forms/{form_key}
```

- 响应应返回 `form_key`、`module_source`、`industry`、`version`、`schema_json`。
- 只返回 `active=true` 的配置。
- 不暴露 admin-only metadata。

验收：

- `GET /api/forms/hvac_quote` 返回 active schema。
- 不存在或 inactive 返回 `404`。
