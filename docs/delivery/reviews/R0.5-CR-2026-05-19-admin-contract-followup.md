## 3. Findings

### P0-1 客户默认环境未配置 ADMIN_API_KEY，后台默认不可用

证据：

- 文件：`clients/dandelion/backend/.env`
- 当前仅包含 `PROJECT_NAME`、`DATABASE_URL`、`ENV`、`PORT`，没有 `ADMIN_API_KEY`。
- 真实 client app 验证结果：

```text
admin_key_configured False
GET /api/admin/dashboard/ 500 {"detail":"Admin API Key not configured on server."}
GET /api/admin/leads/ 500 {"detail":"Admin API Key not configured on server."}
```

影响：

- 前端 Admin 页面即使保存 key，也无法访问后台，因为服务端没有配置可比对的 key。
- R0.5 验收要求“Admin dashboard、lead queue、status update 可用”和“无 admin key 不能访问后台数据”，当前默认客户部署不满足。

修复要求：

- 为 `clients/dandelion/backend/.env` 增加本地开发 `ADMIN_API_KEY`。
- 增加 `.env.example`，明确 `ADMIN_API_KEY` 是后台启用必填项。
- 在 app startup 阶段做 fail-fast：如果启用了 admin/dashboard 模块但没有 `ADMIN_API_KEY`，应在非测试环境直接报错，不要等请求时返回 500。
- 增加测试覆盖：导入 `clients/dandelion/backend/main.py` 的真实 app，并验证默认 `.env` 下 admin API 可用。

验收：

- `ClientConfig.from_env(BASE_DIR / ".env").admin_api_key` 非空。
- 无 key 访问 `/api/admin/dashboard/` 返回 `401`。
- 正确 key 访问 `/api/admin/dashboard/` 返回 `200`。
- 前端 Admin 页面保存相同 key 后能加载 dashboard 和 leads。

### P1-1 公开 `GET /api/leads/` 仍然暴露 lead list

证据：

- 文件：`packages/backend/dandelion_core/modules/leads/router.py`
- `GET /api/leads/` 仍存在且没有 admin auth。
- 真实 client app 验证结果：

```text
GET /api/leads/ 200 {"items":[],"next_cursor":null}
```

影响：

- 一旦有 lead 数据，公开接口会泄露客户线索信息。
- 这直接违反上一轮 review 要求：“公开接口只保留 `POST /api/leads/`，后台读取迁移到 `/api/admin/*`。”

修复要求：

- 删除公开 `GET /api/leads/`。
- 或仅在明确 `ENV=development` 且带开发开关时开放，但默认必须关闭。
- 所有 lead list/detail/status/notes 必须走 `/api/admin/*` 并强制 `X-Admin-Key`。

验收：

- `GET /api/leads/` 返回 `404` 或 `405`。
- `POST /api/leads/` 仍然公开可用。
- `GET /api/admin/leads/` 无 key 返回 `401`，正确 key 返回 `200`。

### P1-2 客户后端部署依赖仍不可复现

证据：

- 文件：`clients/dandelion/backend/requirements.txt`
- 当前只有：

```text
fastapi
uvicorn
python-dotenv
```

- 但 `clients/dandelion/backend/main.py` 直接依赖 shared package，shared package 又需要 `sqlalchemy`、`pymysql`、`pydantic`、`email-validator` 等。
- `clients/dandelion/docker-compose.yml` 中 backend 使用 `build: ./backend`。
- `clients/dandelion/backend` 目录没有 `Dockerfile`。

影响：

- 客户网站独立部署不可复现。
- Docker compose backend build 当前缺少构建入口。
- 与“每个客户网站独立部署、直接引用共享组件”的架构目标冲突。

修复要求：

- 补齐 `clients/dandelion/backend/Dockerfile`，确保能安装客户 backend 依赖和 shared package 依赖。
- 或把 `packages/backend` 做成可安装 package，并在客户 backend requirements 中使用 editable/local path。
- `clients/dandelion/backend/requirements.txt` 必须能独立安装运行所需依赖，不能依赖某个已有 venv。

验收：

- 在干净 Python 环境中安装 `clients/dandelion/backend/requirements.txt` 后可以 import `main.py`。
- `docker compose` backend build 至少有 Dockerfile 和明确 build context。
- 不依赖 `packages/backend/.venv`。

### P1-3 migration 文件带破坏性 drop table，不能作为生产 baseline

证据：

- 文件：`packages/backend/dandelion_core/database/migrations/0001_initial_schema.sql`
- 开头包含：

```sql
SET FOREIGN_KEY_CHECKS = 0;
DROP TABLE IF EXISTS notification_logs;
DROP TABLE IF EXISTS lead_notes;
DROP TABLE IF EXISTS events;
DROP TABLE IF EXISTS leads;
SET FOREIGN_KEY_CHECKS = 1;
```

影响：

- 如果误用于已有客户数据库，会直接删除生产数据。
- 这不符合 migration-first 的安全要求。

修复要求：

- `0001_initial_schema.sql` 应只负责幂等创建，不应 drop。
- 如需本地重置，单独提供 `reset_local_database.sql` 或脚本，并明确只允许开发环境使用。
- migration 文件应使用 `CREATE TABLE IF NOT EXISTS` 或通过正式迁移工具管理。

验收：

- `0001_initial_schema.sql` 不包含 `DROP TABLE`。
- 本地 reset 脚本与生产 migration 分离。

### P2-2 Admin lead contract 字段映射不完整
