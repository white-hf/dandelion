## 3. Findings

### P1-1 `select` options 未做后端校验

证据：

测试 schema：

```json
{
  "fields": [
    {"name": "need", "type": "text", "required": true},
    {"name": "service_type", "type": "select", "options": ["repair", "install"], "required": true}
  ]
}
```

提交：

```json
{
  "form_key": "review_i062",
  "contact_name": "Review Bad Select",
  "email": "review-bad@example.com",
  "data": {
    "need": "quote",
    "service_type": "invalid"
  },
  "consent": true
}
```

实际结果：

```text
invalid_select 200
```

影响：

- 后端没有真正实现动态字段类型校验，只实现了 required presence。
- 前端即使按 schema 渲染 select，下游仍可绕过前端提交非法选项。
- 这不满足 `I0.6.1` 的“动态字段校验逻辑”目标。

修复要求：

- 对 `schema_json.fields` 中 `type == "select"` 的字段，校验提交值必须在 `options` 中。
- 对 `checkbox` 至少校验 boolean。
- 对 `email` 类型字段校验 email 格式；如果 email 字段在 `data` 中出现，也应检查。
- 对未知 field type 返回明确错误或按 text 处理，但策略必须写清楚。
- 校验失败返回 `422`，并包含字段名和错误原因。

验收：

- 非法 select option 返回 `422`。
- 合法 select option 返回 `200`。
- pytest 覆盖该场景。

### P1-2 API contract 与计划/脚本漂移

证据：

- `docs/delivery/Iteration_Plan.md` 的 I0.6.1 范围仍写的是“后端通用 `POST /api/submissions` 适配器”。
- 旧 review 的验收和现有脚本仍使用 `/api/submissions/`。
- 当前 router 实际实现：

```text
GET /api/forms/{form_key}
POST /api/forms/submit
```

- 真实验证：

```text
old_submissions_route 404
```

影响：

- 已有脚本 `scripts/test_i061.py`、`scripts/test_dynamic_forms.sh` 仍会打到旧接口。
- 架构师报告中的接口规范与原计划不一致，但没有先更新产品/技术计划。
- 如果前端 Agent 直接读计划，会实现错 endpoint。

修复路径二选一：

- 方案 A：保留新设计，更新 `Iteration_Plan.md`、测试脚本和 review 验收口径，把标准 contract 改为 `GET /api/forms/{form_key}` + `POST /api/forms/submit`。
- 方案 B：保留向后兼容 alias，让 `POST /api/submissions/` 继续可用并调用同一 service。

验收：

- 文档、脚本、pytest、实际 router 使用同一套 endpoint contract。
- 如果保留旧 route，`POST /api/submissions/` 应返回 `200`。
- 如果废弃旧 route，删除或更新所有旧脚本引用。
